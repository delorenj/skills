# Cache, Connect and credential operations

## Cache contract and security

The intended wrapper selects Connect only for documented supported reads, then uses local Redis as a process-level cache. Native 1Password CLI itself has `OP_CACHE`; do not confuse its own setting with custom Redis cache semantics. Established source behavior is 24h fresh, up to 30d stale fallback on retryable refresh failure (4s refresh timeout), 30s mutation grace, single-flight, and fall-through to native `op` on Redis/unmodeled-input failure. Failures/OTP outputs are never cached. A stale result exits successfully with an `op-cache:` stderr warning; never mistake it for authoritative post-write readback. If Mac port does not implement and test each property, describe actual behavior rather than claiming parity.

Cache contents are **plaintext secrets** even though Connect's own shared volume is encrypted. Redis is already deployed in dedicated `studio-onepassword` project, loopback `127.0.0.1:6379`, with appendonly persistence and a named volume. Recheck owner, binds and health on the Mac before use. Protect disk, backups, volume access and Docker socket; prohibit public Redis endpoint. No second Redis, no `down -v`, no shared service restart for tests. Redis client parser assumptions: local `redis://host:port/db` or known Unix socket; do not infer TLS URL support. Portability of Linux `/proc` lock ownership is unproven on Mac; `kill(pid,0)` alone cannot detect PID reuse or zombies. Pin desktop account (`OP_ACCOUNT` or explicit `--account`) or bypass custom cache; flush after account/permission changes. Unpinned desktop reads must never reuse entries under a wrong identity.

Use **installed** helper help, not guessed flags. If port preserves the canonical interface: `op-cache stats` for counters and Redis health, `op-cache list` for labels/ages, `op-cache flush <ref>` for out-of-band updates, `op-cache invalidate` to mark entries stale, `op-cache disable|enable` for kill switch, and `OP_CACHE=off op read <ref> >/dev/null` for one-off authoritative bypass. `flush --all` removes all entries only when deliberate; never flush shared resources on speculation. No value-reading Redis commands. If Redis unavailable, wrapper should fall through to the same authenticated native/Connect CLI; isolation test changes only one process URL to a closed loopback port. Refresh after web/UI edits, token rotation, account/permission changes, or Connect sync lag; fresh/stale selection and timeout should be visible as redacted metadata.

## Rotations and restart

1. Identify current scope and consumers without printing the token or secret; issue a new, narrower token through owner-secure dashboard/CLI capture. Save it independently of the Connect server it authenticates to; avoid log/stdout capture in agent transcript.
2. Switch one consumer, test its intended read and independently authoritative readback with custom cache bypass; then switch remaining consumers. Explicitly flush the reference that bootstraps Connect when it changes, rather than trusting mutation invalidation of the retained bootstrap entry; keep it warm. Revoke old token only after all consumers verified. A Connect token change changes cache key identity; remove old cached entries after migration. For compromised token, revoke promptly and accept controlled downtime.
3. Back up private `1password-credentials.json` and Connect data volume under owner-controlled encrypted storage; do not commit or expose them. Recreate token and server credentials only through official procedure if lost. Connect API+sync use their own volume, not the Redis volume. Test API and sync health and read-only item access after image updates/restarts. Verify arch/pins against latest official docs before upgrading, keep rollback and backup. Cloud outages and throttling are distinct from local Redis outage.
4. Redis memory/AOF/backups are sensitive. Decide retention with owner; 30d stale ceiling can return old secrets during outage, so high-risk rotations require bypass/invalidation and fail-closed application policy where appropriate. Do not use stale secret as proof of a successful rotation.

## Failure triage (no secret logs)

- Native `op whoami`/account selection fails: fix owner desktop integration or independently authorized identity first; never silently switch to a different account. Empty `op account list` means no configured CLI account at that moment, not a permanent observation.
- Connect creation denied: verify eligible account/group Secrets Automation manage permission and a non-built-in vault; do not assume service account can administer it. No token or credentials = no Connect deployment claim.
- API reachable, item denied: verify token vault scope, per-app token, actual field names and sync health. A remote URL is not equivalent to authorization. For another Mac, verify selected Tailscale TLS endpoint and access restrictions, never publish bare HTTP.
- Read hit but mutation invisible: inspect cache age, 30s grace and stale warning; bypass cache for authoritative readback, flush targeted reference, verify Connect sync independently.
- Redis timeout/memory pressure: metadata-only stats and container health; test native fall-through with isolated override, not a destructive shared restart. If running against wrong Redis or unexpected remote host, disable custom cache immediately.
- Wrapper works interactively but fails in launchd or agent: inspect PATH, Python runtime, native CLI direct path, environment stripping, owner auth and token bootstrap, with redacted diagnostics. Avoid Linux `systemctl`, `readlink -f`, `sha256sum`, hardcoded `/usr/bin` or a bare `/proc` assumption.

Record observed outcomes and deferred tests in a redacted receipt. Never paste tokens, `op read`, item JSON, Redis payloads, resolved dotenv, or service logs that contain credentials.
