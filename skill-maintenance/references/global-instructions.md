# Trimming global instructions

Global instructions are paid attention on every task. Keep stable user preferences,
real authorization boundaries, and short routing to procedures; require a reason
for a lengthy operational section to remain global.

1. Read the live instruction file and identify how each client obtains it. Two
   pasted versions or generated views are not necessarily two editable sources.
2. Build a section-to-owner map. For each rule, locate the actual skill and its
   operative reference or script. Classify it as a user invariant, a task-specific
   procedure, a mutable inventory, an incident narrative, or a duplicated command.
3. Cross-examine the owner before deleting the global fallback. A reference to a
   skill that teaches a stale bank resolver is not equivalent coverage. Repair
   and check the owner, including caller links and discoverability, first.
4. Retain the minimum stable rule where removal would change user intent. Move
   algorithms and troubleshooting to their owner. Delete repetition, emotional
   emphasis, obsolete TODOs, provider price lists, and copied hook implementation
   detail. Summarize the user's risk tolerance without carrying a historic warning
   dialogue into every task. Do not erase their commit/push authorization while
   removing its repeated explanations.
5. Read the candidate as an agent handling an unrelated request. It should not
   demand a repo-wide migration, all-repo cleanup, scheduler rewrite, or provider
   optimization just because the task happened to touch a nearby subject.

Useful ownership examples from this audit:

| Global topic | Keep globally | Procedure owner |
| --- | --- | --- |
| Memory | Use relevant project history | hindsight plus shared bank helper |
| Git delivery | Commit/push/integrate task changes; preserve unrelated WIP | merge-forward |
| Repository debris | Source belongs in Git; generated runtime state does not | gitignore-maintenance |
| Agent projections | A canonical source and generated views | skillex-skill-registry for skills; agent-config-fanout for hooks |
| Secrets | Vault/process references; never plaintext credentials in files | delonet-dotenv |
| Networking | Stable identity and hostname preference | service-specific references |
| Provider wiring | Key type and ownership invariants | scoped provisioning procedure |

Measure before/after lines or words honestly. Shorter is a result, not the
acceptance criterion: the agent must still find the correct procedure, honor
user authorization, and avoid the original failure. Distinguish edits made from
review-only recommendations and preserve an evidence-linked cut/move/keep record.
