# Antislop shared criteria

The user's brief, existing product identity, accessibility, and correct behavior
are the decision criteria. This package does not impose a font, color, punctuation,
layout, or animation style on every task. Apply only criteria relevant to the
requested surface. Do not rewrite unrelated work or require an install wizard.

Use the companion that fits: `antislop-code` for comments, `antislop-copywriting`
for prose, `antislop-ui` for visual review, and `antislop-human` for accessibility.
Their R-number references resolve to this table. Examples are warning signs,
not evidence that a style is wrong in the user's context.

## Rule reference

| Rule | Criterion |
| --- | --- |
| R-01 | Use gradients and color effects for a concrete identity or hierarchy purpose. |
| R-02 | Write clearly in the user's voice; punctuation is not a universal style ban. |
| R-03 | Verify responsive behavior against the actual content and supported viewports. |
| R-04 | Use icons with a recognizable meaning and accessible labels when needed. |
| R-05 | Let content and user tasks determine page structure. |
| R-06 | Choose typography from product identity and reading needs, not a banned-font list. |
| R-07 | Background treatments must support content rather than obscure it. |
| R-08 | Use arrows to communicate direction or action, not as automatic decoration. |
| R-09 | Badges communicate real status or information. |
| R-10 | Use transparency only where layering remains readable. |
| R-11 | Use consistent, purposeful component shapes. |
| R-12 | Use shadows to explain elevation or focus. |
| R-13 | Use glow sparingly when it has a product purpose. |
| R-14 | Card grouping and hierarchy should reflect the information. |
| R-15 | Action labels say what happens next. |
| R-16 | Replace generic marketing claims with supported specifics. |
| R-17 | Never invent data or metrics. |
| R-18 | Never invent testimonials or endorsements. |
| R-19 | Motion has a UI purpose; avoid endless loops by default and support reduced motion. |
| R-20 | Preserve or deliberately establish a coherent product identity. |
| R-21 | Theme choice follows the brief; validate every theme actually shipped. |
| R-22 | Illustrations connect to real content; they are optional. |
| R-23 | Ask for missing facts or required assets only when needed; use available authorized assets. |
| R-24 | Navigation and links work and have meaningful destinations. |
| R-25 | Measure contrast; do not guess that colors pass. |
| R-26 | Controls work with their supported input methods and communicate disabled states. |
| R-27 | Provide relevant loading, empty, success, and error states. |
| R-28 | Use FAQs only when they answer real user questions. |
| R-29 | Palette complexity follows a coherent design system, not an arbitrary universal color count. |
| R-30 | Honor references and the brief without accidentally copying unrelated product identity. |
| R-31 | Be able to explain material design decisions; do not manufacture justification documents. |
| R-32 | Preserve keyboard access, meaningful focus, and appropriate semantics. |
| R-33 | Use the smallest reviewable editing method; preserve unrelated code and behavior. |
| R-34 | Verify legibility and state behavior in every theme actually delivered. |
| R-35 | Verify affected behavior and describe real limits before delivery. |
| R-36 | Do not fabricate claims, history, or customer evidence. |
| R-37 | Resolve design direction when changing identity; preserve incumbent direction for refinement. |
| R-38 | Use real content or label necessary placeholders honestly. |

## Delivery check

Confirm that the requested change preserves factual truth and user intent,
works in its relevant states, and was checked at the changed boundary. Report
remaining concrete limitations. Do not add reviews, docs, or stylistic changes
just to satisfy an unrelated checklist.

C-1 means intentional decisions; C-2 functional completeness; C-3 content-driven
composition; C-4 resilient states/input; C-5 evidence-backed claims.
